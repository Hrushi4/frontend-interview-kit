Interactive · AI scoring pipeline

Why concurrency gave the scoring pipeline 5x throughput

Each call waits on transcription and LLM APIs, so the work is I/O-bound. Drag the worker concurrency and run a batch of 12 calls. The provider's rate limit caps useful concurrency.

80calls per hour
1.0×vs sequential
45 savg latency per call
1effective in flight
Above 5 in flight, the LLM provider returns 429s. Extra concurrency only adds retries, so the useful limit is 5.

Illustrative model: 45 s per call, provider limit of 5 concurrent requests. Replace with your measured numbers.

webhook→ transcribe→ chunk→ score (LLM)→ validate→ save + SSE
Interview: system design or "how did you get 5x?""Most of the time was waiting on APIs, not CPU. Watch: at 1 in flight it's sequential. At 5 we're at the provider's limit, about 5x. Past that we only create 429s, which is why we added a shared rate limiter instead of just adding workers." Then open the AI pipeline case study for retries, idempotency and dead letters.

What changed when permissions moved from the UI to the server

An illustrative role × endpoint matrix, the same kind of test that now runs in CI. Red means an endpoint answered a role it should have refused.

8 critical findings

Example endpoints for illustration. Your real findings: RBAC enforced only in the UI, token handling, PHI in logs. 85% fewer findings on re-audit.

Interview: ownership and security questions"Nobody assigned this. I mapped every role and tested every endpoint as each role and tenant. Before, the UI hid buttons but the API accepted the calls. After, every FastAPI route declares a permission and every query is scoped by tenant. This matrix runs in CI so it can't regress." Toggle before/after while you talk.
